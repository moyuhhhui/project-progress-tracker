# LLM 多项目业务工具设计

## 目标

把当前“LLM 只能返回一个 JSON Action”的解析链路改为受控工具调用：LLM 可以针对一条企业微信或网页消息调用多次项目业务工具，每次调用对应一个明确的项目操作。包含六个项目的消息应分别产生六个可校验、可审计的项目结果，不能再把整段原文保存为一个“待整理”项目。

## 当前问题

- `ParsedMessage` 继承单个 `Action`，一次响应只能表达一个 `intent`。
- 系统提示词明确要求“不同项目不要合并”，但输出契约没有多操作表达能力，规则与接口互相冲突。
- 企业微信群消息自动保存时，单个 Action 校验失败会进入兜底分支，把整段原文截断为 `待整理：...` 项目名。
- 模型识别出的多个项目只留在 `evidence`，没有可执行结构，因此最新消息最终错误生成了 `P0005`。

## 方案

采用“LLM 工具调用 + 后端受控执行器”，不允许模型直接访问数据库。

### 1. 工具边界

向模型注册以下业务工具，参数结构从现有 Pydantic 业务模型生成，避免提示词和数据库字段各写一套：

- `record_project_item`：记录新项目或已有项目的一个或多个事项；项目不存在时可按明确项目名创建。
- `create_project`：只创建项目基本资料，没有具体事项时使用。
- `edit_project`：修改项目资料和负责人分工。
- `add_milestone` / `edit_milestone`：新增或修改目标节点。
- `report_progress`：记录节点进度、阻塞和下一步。
- `change_project_status` / `change_milestone_status`：更新状态。
- `query_projects`：查询候选项目，不产生写入。

工具调用参数统一包含 `project_id`、`milestone_id` 和对应业务 `data`；未使用的字段省略，不允许输出 `null`。负责人使用结构化的 `owner_assignments`：

```json
[
  {"name": "小柯", "role": "A角", "primary": true},
  {"name": "小朱", "role": "B角", "primary": false}
]
```

`A角` 已表示主负责人，不再额外生成“主负责人”角色。

### 2. 调用与执行流程

1. 后端根据当前用户权限召回候选项目和成员，只把可见候选发给模型。
2. 模型分析消息并发出零到多次工具调用；不同项目必须分别调用。
3. 后端将每次调用转换为现有 `Action`，用 Pydantic 和 `Service.propose` 校验，不接受模型提供数据库内部字段。
4. 写操作仍由现有 `Service.create_draft(..., auto_save=True)` 完成，从而保留权限、版本、审计和项目名称冲突检查。
5. 一条消息最多允许 20 次业务工具调用，最多进行 8 轮模型/工具交互；超过上限整条消息停止并返回明确错误。
6. 所有调用完成后返回批量结果：成功项包含项目编号和操作类型，失败项包含对应项目名称和可公开的业务原因。

单项目消息保持现有返回形态，避免影响网页草稿页；多项目消息新增 `kind="batch"`，包含 `drafts`、`failures` 和汇总数量。

### 3. 系统提示词

系统提示词只描述业务语义和选用哪个工具，不再要求模型手写顶层 `output_schema` JSON。核心规则：

- 一段文字包含多个项目时，按项目边界拆分，每个项目至少调用一次工具。
- 同一项目的多个安排放入一次 `record_project_item.items`，不同项目禁止合并。
- 项目名称、负责人、日期、状态只提取原文明示内容；不确定字段省略。
- `确认时间` 按上下文落为事项 `time_text`；只有具体到日期时填写 ISO `due_date`。
- “下周”“尽快”等只保留 `time_text`，不得编造日期。
- 新安排的“进行中”是事项状态，不代表整个项目状态。
- 已存在且唯一匹配的项目必须使用候选 `project_id`，不得重复创建同名项目。
- 模型只能调用已注册工具；不得声称已经保存，也不得输出数据库 ID、审计或版本字段。

### 4. 企业微信回执

- 全部成功：`已处理 6 个项目，成功保存 6 项。`
- 部分成功：`已处理 6 项：成功 5 项，失败 1 项。`，随后逐条列出失败项目及原因。
- 全部失败：明确说明未保存任何项目，并引导重新描述或使用网页录入。
- 查询调用继续返回工作台入口。
- 同一企业微信 `msgid` 继续复用现有消息幂等键，重复回调不得再次执行工具。

### 5. 错误与安全

- 工具仅封装 Action，不向模型开放数据库连接、SQL、文件、网络或任意代码执行能力。
- 每次调用必须经过现有权限与业务校验；模型给出的项目 ID 必须来自候选集合。
- 解析失败不能再创建“待整理”项目；无法归属的项目操作作为失败项返回。
- 单个调用失败不阻止其他独立项目保存，但必须在最终回执中显式报告。
- 不在群回执中泄露其他项目名称、成员权限或内部异常堆栈。

## 兼容性

- 保留现有网页单 Action JSON 解析作为短期兼容路径和测试注入接口。
- 真实 DeepSeek 调用改为工具调用模式；不再同时强制 `response_format=json_object`。
- 现有 `projects`、`drafts`、`audit` 表结构不变；批量结果保存在现有 `messages.response` 中。
- 当前错误的 `P0005` 不自动删除或重写，避免擅自修改已入库数据。

## 验收标准

- 给定包含六个明确项目的同一条消息，模型可产生六次业务工具调用，数据库出现六个独立项目或对已有项目的独立更新。
- 每个项目的负责人分工、事项、原始时间文字和明确日期分别落入对应字段。
- 多项目之间不存在原文串入项目名或事项的情况。
- 单项目网页消息、企业微信去重、权限校验、审计和现有状态更新测试继续通过。
- 工具调用超限、未知工具、非法字段、重复项目名和部分失败都有自动化测试。

## 非目标

- 本次不自动清理 `P0005` 或重新播放历史消息。
- 本次不修改大屏样式。
- 项目颜色区分度属于独立的前端样式改动，单独确认和实施。
