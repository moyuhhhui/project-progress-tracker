# 企业微信 AI 录入与后台任务可靠性蓝图

日期：2026-09-09  
状态：待评审  
范围：企业微信群录入、AI 工具调用、项目内容编辑、状态简化、批量保存、运行进程、提醒扫描与诊断能力

## 1. 背景与目标

当前系统已能通过企业微信群消息识别项目安排，并把信息保存到项目数据库。但现场使用暴露出一种危险的“半成功”体验：一条消息的有效部分已经入库，群回复却同时显示多项失败，且失败数量被误写成“项目数量”。操作者难以判断哪些内容已经保存、是否应重发，以及重发后会不会产生重复数据。

本蓝图的目标是保留现有 FastAPI、SQLite、DeepSeek 工具调用和企微长连接架构，在不重写整套系统的前提下，建立一条可验证、可追踪、不会误导用户的录入链路：

- 模型的无效尝试不计入业务项目或事项数量。
- 模型参数全部通过校验后，业务层才开始保存。
- 允许真实的批量业务操作逐项成功或失败，但必须准确展示结果。
- 重复消息、超时和回复失败不会导致重复写入。
- 日志能定位失败字段，同时不记录密钥或完整业务内容。
- Web、企微接收和提醒进程明确使用同一个数据库与同一套配置。
- 负责人缺失时提醒扫描降级为可见的阻塞记录，不得使整个 worker 周期失败。
- 企业微信群内任何成员只要 @机器人即可发起录入，不做成员身份绑定、白名单或角色权限校验。
- 不设置待确认的中间业务状态：信息完整时直接保存，信息不完整时明确提示缺失字段且不写业务数据。
- 新建项目和事项直接进入“进行中”，移除“前期准备/未开始”状态。
- 前端提供统一的“项目内容编辑”，可直接维护项目基本信息和项目事项/节点。

- AI 已配置，当前模型为 `deepseek-v4-flash`。
- 公司内部共享模式的产品规则确定为：字段完整时直接保存，字段不完整时不写业务数据并回复缺失内容。

## 3. 根因分析

### 3.1 模型重试与业务结果混在一起

当前工具循环在每轮收到模型调用后立即调用参数转换函数。转换失败时，错误被加入 `planned_failures`，同时把失败结果返回给模型继续修正。模型后续重试时，先前的失败仍保留。最终群回复把所有历史失败尝试和成功调用相加，因此一次逻辑请求会被放大成多个“项目”。

根因不是 SQLite 保存失败，而是“模型尝试次数”和“最终业务计划”共用同一个结果模型。

### 3.2 校验发生在模型循环内，但保存边界不清晰

目前有效调用被加入计划、无效调用被加入失败列表。模型结束后，有效调用仍会保存，因此出现“参数有错但部分内容已入库”。部分保存本身可以是合理产品策略，但只有在失败属于真实业务冲突时才应发生；模型内部格式重试不应暴露为业务失败，更不应与最终计划一起保存和计数。

### 3.3 诊断信息过度收缩

`ValidationError` 被统一转换为一条固定文案。这样避免了向群里泄漏数据，但也让后台失去字段级证据。系统需要区分：

- 用户可见错误：简洁、不泄漏内部结构。
- 后台诊断：只保存字段路径、错误类型、工具名、轮次和调用标识，不保存字段值、密钥或完整原文。

### 3.4 进程和数据库缺少统一身份

Web 后端、企微接收 worker、提醒 worker 和前端分别启动，环境变量需要在每个终端重新注入。状态页面只显示企微租约阶段，不能证明所有进程使用同一个数据库文件、配置版本和代码版本。这使“群里有回复但当前数据库没有消息”难以快速定位。

### 3.5 提醒模型与负责人数据模型不兼容

项目支持以姓名和 A/B 角保存结构化负责人，但提醒表要求非空的系统用户 ID。扫描逻辑在负责人无效时本想创建 `blocked` 记录，却仍把空 `owner_id` 写入非空列，导致整个事务回滚。数据允许“只有姓名”，提醒表却假定“一定绑定系统用户”，两者契约冲突。

### 3.6 待确认流程和“未开始”增加了不必要的中间状态

现有代码仍包含待确认记录及对应前端页面，用户需要理解“待确认、已确认、已保存”之间的区别；项目和事项又存在“前期准备/未开始”，与“进行中”的实际使用边界不清晰。这些中间状态增加确认成本，也使自动保存、自动完成和群回复更难解释。

目标产品规则应简化为：内容完整就直接保存，内容不完整就不写业务表并一次性说明缺少什么；新建业务对象默认进入“进行中”。

### 3.7 前端编辑范围过窄且依赖待确认流程

当前项目详情页已有“编辑项目信息”入口，但只覆盖项目基本字段，提交结果仍进入待确认流程，项目事项/节点需要在其他入口分别维护。目标方案需要把基本信息和事项/节点组织为一次明确的“项目内容编辑”操作，并直接保存到正式项目数据；现有待确认页面不再承担编辑职责。

## 4. 推荐方案

采用“加强现有链路”的方案，不重写 AI 接入。

### 4.1 两阶段 AI 处理

将一次消息处理拆为两个明确阶段。

#### 阶段 A：规划、修正和归一化

1. 模型可以调用业务工具，但调用仅进入内存中的候选计划，不写数据库。
2. 每次工具调用先经过 JSON Schema 和 Pydantic 校验。
3. 无效调用以脱敏错误返回模型修正，但不加入最终业务失败列表。
4. 同一个 `tool_call_id` 或同一业务指纹的重试只保留最后一次结果。
5. 对同项目、同动作、同日期的候选事项进行确定性去重。
6. 模型结束时生成唯一的“最终执行计划”；若仍有未修复的格式错误，则整条消息不进入保存阶段。

对于“明后两天去锐翰工厂调研”，最终计划必须只有两个事项：相同书面化标题、两个不同截止日期、同一个项目 ID。

#### 阶段 B：业务执行

1. 只执行阶段 A 已完全通过格式与业务规则预检的最终计划。
2. 每个真实业务动作保留独立结果，允许名称冲突、版本冲突等业务原因导致部分成功。
3. 模型格式错误不再出现在“业务失败”中。
4. 每个动作生成稳定业务指纹，用于同消息内去重和跨回调幂等。
5. 保存完成后持久化最终执行摘要，再生成企微回复。

### 4.2 重新定义批量结果

统一使用以下计数：

- `recognized_actions`：最终计划中识别出的业务动作数。
- `saved_actions`：实际保存成功数。
- `business_failures`：通过格式校验但因版本冲突、名称冲突或其他业务规则失败的动作数。
- `model_retries`：仅后台诊断使用，不向用户表示为项目数。

群回复示例：

> 已识别 2 项安排，成功保存 2 项，失败 0 项。已保存内容可在工作台查看。

只有真实业务失败时才逐项显示项目名称和可操作原因。回复中禁止使用“处理 N 个项目”，除非计数对象确实是去重后的项目。

### 4.3 脱敏诊断

为消息处理结果增加结构化诊断，建议字段包括：

- 消息内部 ID。
- 模型与代码版本。
- 工具名、工具调用轮次、工具调用 ID 的哈希。
- 校验错误字段路径，例如 `data.items.1.due_date`。
- 错误类型，例如 `date_type`、`extra_forbidden`、`missing`。
- 是否在后续轮次修复。
- 最终计划动作数、去重数和保存结果数。

禁止保存：API Key、企微 Secret、完整工具参数、完整群消息副本和未经脱敏的 SDK 响应。用户群回复仍只显示业务级文案。

### 4.4 回复失败与保存成功分离

消息处理状态需要拆分为：

- `processing`
- `saved`
- `replying`
- `done`
- `reply_failed`
- `failed_before_save`

保存成功后，即使企微最终回复失败，也不得把消息标成业务处理失败。状态页和日志应明确显示“已保存，回复失败”，并提供工作台检查入口。不得自动重放业务保存；只能在确认平台未接收时重试回复。

### 4.5 统一进程启动和身份

新增统一启动脚本，负责启动并检查：

1. FastAPI Web 后端。
2. Vite 前端开发服务或后端静态构建服务。
3. 企业微信接收 worker。
4. 提醒 worker。

统一启动器必须：

- 只加载一次 `.env`。
- 把同一个绝对 `TRACKER_DB` 传给所有后端进程。
- 启动前检查端口、进程租约和重复实例。
- 为各进程建立独立日志文件和 PID/启动时间记录。
- 在状态接口展示数据库路径哈希、代码版本、进程启动时间和最近心跳。
- 退出或重启时只操作由该启动器创建的进程。

企微启用时，配置检查必须拒绝 `localhost`、`127.0.0.1` 和其他员工手机不可访问的 `TRACKER_WEB_URL`，并提示配置局域网地址或 HTTPS 域名。

### 4.6 修复提醒负责人契约

推荐把提醒记录的收件人改为可空系统用户引用：

- `owner_id` 允许为空。
- 无系统用户 ID 时创建 `blocked` 提醒记录，详情为“负责人未绑定系统成员”。
- `dispatch` 只处理存在有效 `owner_id` 和企微 UserID 的记录。
- 管理页集中展示阻塞提醒，指导管理员完成绑定。
- 后续负责人结构中增加可选的系统用户 ID；姓名和 A/B 角继续用于展示，系统 ID 仅用于定向发送提醒，不用于群录入权限判断。

SQLite 迁移需要重建 `reminders` 表，在事务中复制数据、重建索引并核对行数。迁移前必须执行在线备份，不得直接覆盖唯一数据库文件。

### 4.7 企业微信群触发规则：@机器人即可

群聊采用内部共享入口，不建立成员身份绑定或业务权限体系：

- 群内任何成员 @机器人并附带业务内容，即可触发 AI 识别与保存。
- 不检查发送者是否绑定系统用户，不维护成员白名单，不按角色限制项目新增或修改。
- 不 @机器人时忽略消息，避免机器人处理普通群聊内容。
- 仍记录企微群 ID、消息 ID、发送者企微标识的不可逆哈希、处理时间和业务审计摘要，用于幂等和问题追踪；该记录不作为权限判断依据。
- 企微 SDK/平台连接自身所需的凭证校验继续保留，这属于机器人接入安全，不属于群成员身份校验。

### 4.8 只保留直接保存流程并移除“前期准备”状态

目标系统不再创建、确认或展示待确认业务对象：

- 企微 AI 只有两种业务结果：最终计划完整且合法时直接保存；存在缺失、歧义或无法修正的字段时保存 0 项，并一次性回复缺失字段和重新发送示例。
- 前端删除现有待确认页面、导航入口、路由、操作按钮及相关状态类型；新增和编辑统一进入“项目内容编辑”。
- 前端新增和编辑均直接写正式项目数据，不调用 `/api/drafts`，不出现二次确认页面或消息状态。
- 后端删除 `/api/drafts` 的创建、查询、确认和拒绝接口，并移除只服务于该流程的模型与服务代码。
- 同一版本的数据迁移删除对应业务表；已成功写入正式项目的数据以项目和审计记录为准，未确认的遗留中间记录不导入正式业务表。
- 消息处理记录继续保留，仅用于幂等、诊断和回复重试，不能被人工确认后再次执行。

状态模型同步简化：

- 删除项目与事项的 `not_started` 状态及“前期准备/未开始”文案。
- 新建项目和事项默认状态为 `active`（进行中）。
- 数据迁移把现有 `not_started` 统一转换为 `active`，保留原创建时间和审计历史。
- 筛选器、统计卡、看板、日历、提醒和状态转换规则不得再生成或依赖 `not_started`。

### 4.9 前端“项目内容编辑”

在项目详情页提供统一的“编辑项目内容”入口，直接维护两类内容：

1. 项目基本信息：项目名称、描述、对接公司、联系人、联系方式、负责人、成员、A/B 角、开始日期、截止日期和展示开关。
2. 项目事项/节点：标题、说明、负责人、开始日期、截止日期、状态、进度和显示顺序；支持新增、修改、调整顺序和取消事项。取消采用状态与审计记录，不做无痕物理删除。

编辑器采用一次提交、服务端原子保存：

- 打开时取得项目当前版本，提交时携带 `expected_version` 和必填的变更原因。
- 服务端先校验整个项目和全部事项；任何字段不合法时全部不写入，并把错误定位到对应表单字段。
- 校验通过后在一个事务中保存项目信息、事项变更和审计记录，避免基本信息已改但事项失败。
- 若版本已被其他人更新，返回冲突并保留用户当前输入，由用户刷新对比后再提交。
- 保存成功后刷新项目详情、进度统计、看板和日历；不生成待确认记录，不需要二次确认。
- 因为群入口不做身份校验，前端编辑同样不新增角色权限系统；只记录变更来源和操作摘要。

## 5. 数据流

```text
企微回调
  → 企微事件接收与 @机器人判定
  → 消息幂等检查
  → AI 候选调用（只在内存）
  → 参数校验、模型修正、业务去重
  → 最终执行计划
  → 业务规则与版本预检
  → 逐动作保存并记录业务结果
  → 持久化消息处理摘要
  → 生成准确群回复
  → 发送回复并单独记录回复状态
```

任何模型格式错误必须止于“参数校验、模型修正”阶段；任何企微发送错误必须发生在业务保存完成之后，并拥有独立状态。

## 6. 测试与验收

### 6.1 AI 规划测试

- “明后两天去锐翰工厂调研”只形成两个最终事项。
- 模型先返回错误结构、再返回正确结构时，只统计最终正确动作。
- 同一事项被模型重复调用时只保存一次。
- 模型所有轮次都无法修正时保存 0 项，并返回可重试提示。
- 失败诊断包含字段路径和错误类型，不包含字段值和原文。

### 6.2 批量业务测试

- 两个合法动作均保存时，回复为识别 2、保存 2、失败 0。
- 一个动作存在版本冲突时，只把该动作计为业务失败。
- 重放同一个企微 `msgid` 不产生新项目、节点或审计记录。
- 相同文本使用新的消息编号时，业务指纹避免十分钟内重复新增。

### 6.3 回复状态测试

- 保存成功、最终回复失败时，消息状态为 `reply_failed`，项目仍只保存一次。
- 回复重试不得重新调用模型或重新执行业务动作。
- SDK 断线和超时日志不包含凭证与完整消息正文。

### 6.4 进程一致性测试

- 四个进程显示同一个数据库路径哈希。
- 重复启动企微接收进程被拒绝并明确指出现有实例。
- 状态页能区分未启动、离线、已认证、消息处理错误和回复错误。
- `TRACKER_WEB_URL` 为回环地址时，企微启动检查失败。

### 6.5 提醒测试

- `owner_id` 为空时创建阻塞记录而不是抛出 `IntegrityError`。
- 一个无负责人节点不会阻止其他节点生成提醒。
- 自动完成成功、提醒扫描失败时必须分别记录结果，周期日志不能只显示笼统失败。
- 负责人绑定后，下一次扫描把阻塞记录转为可发送状态。

### 6.6 群触发与直接保存测试

- 群内任意成员 @机器人时均可触发处理，不要求系统账号绑定或白名单。
- 未 @机器人时不调用模型、不写项目数据。
- 内容完整时直接保存正式项目和事项，不产生待确认记录。
- 内容缺少必要字段时保存 0 项，回复明确列出缺失字段；补充信息作为新消息重新解析，不读取旧的中间记录。
- 前端不存在待确认页面、导航入口或路由，相关 URL 返回未找到或跳转到项目列表。
- 重放同一消息时只返回原处理结果，不重复保存。

### 6.7 状态简化测试

- 新建项目和事项默认状态均为 `active`。
- 历史 `not_started` 数据迁移后全部为 `active`，数量、日期和审计历史保持一致。
- API、前端筛选器、看板、日历和提醒流程均不再显示或产生“前期准备/未开始”。

### 6.8 项目内容编辑测试

- 一个页面可加载并修改项目基本信息及其事项/节点。
- 基本信息与多个事项一次提交成功后，只增加一组关联审计记录。
- 任一事项字段非法时，项目基本信息和其他事项均不落库。
- 并发版本冲突时不覆盖新版本，且编辑器保留尚未提交的输入。
- 取消事项保留历史和审计，不执行物理删除。
- 保存后详情、统计、看板与日历显示一致，且不生成待确认记录。

## 7. 实施顺序

### 第一阶段：阻止误导和重复写入

- 分离模型尝试与最终业务计划。
- 对最终计划去重。
- 修正批量计数和企微回复文案。
- 增加对应单元测试和集成测试。

### 第二阶段：简化录入和编辑体验

- 同一版本内删除前端待确认页面及其导航、路由、按钮和类型，删除后端 `/api/drafts` 接口及对应业务表。
- 移除 `not_started` 及“前期准备/未开始”，迁移存量数据为 `active`。
- 增加前端“编辑项目内容”统一页面和原子保存接口。
- 落实群内任何成员 @机器人即可使用的触发规则。

### 第三阶段：增加可诊断性

- 增加脱敏字段级校验诊断。
- 拆分保存状态和回复状态。
- 改进企微 worker 日志与状态接口。

### 第四阶段：统一运行方式

- 增加统一启动、停止和状态检查脚本。
- 增加数据库路径哈希和代码版本标识。
- 对企微工作台地址执行非回环校验。

### 第五阶段：修复提醒数据契约

- 备份数据库。
- 迁移提醒表的可空负责人设计。
- 修复扫描和发送过滤逻辑。
- 增加管理页阻塞原因展示。

## 8. 非目标

- 不更换 DeepSeek 服务商。
- 不引入消息队列或多机分布式架构。
- 不允许模型直接访问数据库、网络或文件。
- 不自动猜测姓名对应的系统用户账号。
- 不建设群成员身份绑定、白名单或角色权限系统。
- 不保留待确认业务对象或二次确认流程。
- 不保留“前期准备/未开始”状态。
- 不在日志中保存密钥或完整模型工具参数。
- 不把整个项目的完成状态改为自动确认；本蓝图只保留现有节点自动完成规则。

## 9. 完成标准

本方案完成后，群内任何成员只要 @机器人即可录入；同样的“明后两天”消息必须只产生两个节点，群回复必须显示“识别 2 项、保存 2 项、失败 0 项”。信息不完整时不得产生待确认记录或部分业务数据。前端待确认页面及相关入口、路由和按钮必须全部删除。新建项目和事项直接进入“进行中”，系统不再显示“前期准备/未开始”。前端可以在一个入口直接编辑项目基本信息和事项/节点，并以一个事务保存。模型内部发生多少次格式修正都不能改变业务计数。后台必须能通过脱敏诊断指出失败字段；企微回复失败不得导致重复保存；提醒扫描遇到未绑定负责人时不得中断整个周期；所有后台进程必须能证明它们使用同一个数据库实例。
