# 企业微信 AI 录入与后台任务可靠性蓝图

日期：2026-09-09  
状态：待评审  
范围：企业微信群录入、AI 工具调用、批量保存、运行进程、提醒扫描与诊断能力

## 1. 背景与目标

当前系统已能通过企业微信群消息识别项目安排，并把信息保存到项目数据库。但现场使用暴露出一种危险的“半成功”体验：一条消息的有效部分已经入库，群回复却同时显示多项失败，且失败数量被误写成“项目数量”。操作者难以判断哪些内容已经保存、是否应重发，以及重发后会不会产生重复数据。

本蓝图的目标是保留现有 FastAPI、SQLite、DeepSeek 工具调用和企微长连接架构，在不重写整套系统的前提下，建立一条可验证、可追踪、不会误导用户的录入链路：

- 模型的无效尝试不计入业务项目或事项数量。
- 模型参数全部通过校验后，业务层才开始保存。
- 允许真实的批量业务操作逐项成功或失败，但必须准确展示结果。
- 重复消息、超时和回复失败不会导致重复写入。
- 日志能定位失败字段，同时不记录密钥或完整业务内容。
- Web、企微接收和提醒进程明确使用同一个数据库与同一套配置。
- 负责人缺失时提醒扫描降级为可见的阻塞记录，不得使整个 worker 周期失败。

## 3. 根因分析

### 3.1 模型重试与业务结果混在一起

当前工具循环在每轮收到模型调用后立即调用参数转换函数。转换失败时，错误被加入 `planned_failures`，同时把失败结果返回给模型继续修正。模型后续重试时，先前的失败仍保留。最终群回复把所有历史失败尝试和成功调用相加，因此一次逻辑请求会被放大成多个“项目”。

根因不是 SQLite 保存失败，而是“模型尝试次数”和“最终业务计划”共用同一个结果模型。

### 3.2 校验发生在模型循环内，但保存边界不清晰

目前有效调用被加入计划、无效调用被加入失败列表。模型结束后，有效调用仍会保存，因此出现“参数有错但部分内容已入库”。部分保存本身可以是合理产品策略，但只有在失败属于真实业务冲突时才应发生；模型内部格式重试不应暴露为业务失败，更不应与最终计划一起保存和计数。

### 3.3 诊断信息过度收缩

`ValidationError` 被统一转换为一条固定文案。这样避免了向群里泄漏数据，但也让后台失去字段级证据。系统需要区分：

- 用户可见错误：简洁、不泄漏内部结构。
- 后台诊断：只保存字段路径、错误类型、工具名、轮次和调用标识，不保存字段值、密钥或完整原文。

### 3.4 进程和数据库缺少统一身份

Web 后端、企微接收 worker、提醒 worker 和前端分别启动，环境变量需要在每个终端重新注入。状态页面只显示企微租约阶段，不能证明所有进程使用同一个数据库文件、配置版本和代码版本。这使“群里有回复但当前数据库没有消息”难以快速定位。

### 3.5 提醒模型与负责人数据模型不兼容

项目支持以姓名和 A/B 角保存结构化负责人，但提醒表要求非空的系统用户 ID。扫描逻辑在负责人无效时本想创建 `blocked` 记录，却仍把空 `owner_id` 写入非空列，导致整个事务回滚。数据允许“只有姓名”，提醒表却假定“一定绑定系统用户”，两者契约冲突。

## 4. 推荐方案

采用“加强现有链路”的方案，不重写 AI 接入。

### 4.1 两阶段 AI 处理

将一次消息处理拆为两个明确阶段。

#### 阶段 A：规划、修正和归一化

1. 模型可以调用业务工具，但调用仅进入内存中的候选计划，不写数据库。
2. 每次工具调用先经过 JSON Schema 和 Pydantic 校验。
3. 无效调用以脱敏错误返回模型修正，但不加入最终业务失败列表。
4. 同一个 `tool_call_id` 或同一业务指纹的重试只保留最后一次结果。
5. 对同项目、同动作、同日期的候选事项进行确定性去重。
6. 模型结束时生成唯一的“最终执行计划”；若仍有未修复的格式错误，则整条消息不进入保存阶段。

对于“明后两天去锐翰工厂调研”，最终计划必须只有两个事项：相同书面化标题、两个不同截止日期、同一个项目 ID。

#### 阶段 B：业务执行

1. 只执行阶段 A 已完全通过格式与权限预检的最终计划。
2. 每个真实业务动作保留独立结果，允许名称冲突、版本冲突等业务原因导致部分成功。
3. 模型格式错误不再出现在“业务失败”中。
4. 每个动作生成稳定业务指纹，用于同消息内去重和跨回调幂等。
5. 保存完成后持久化最终执行摘要，再生成企微回复。

### 4.2 重新定义批量结果

统一使用以下计数：

- `recognized_actions`：最终计划中识别出的业务动作数。
- `saved_actions`：实际保存成功数。
- `business_failures`：通过格式校验但因权限、冲突或业务规则失败的动作数。
- `model_retries`：仅后台诊断使用，不向用户表示为项目数。

群回复示例：

> 已识别 2 项安排，成功保存 2 项，失败 0 项。已保存内容可在工作台查看。

只有真实业务失败时才逐项显示项目名称和可操作原因。回复中禁止使用“处理 N 个项目”，除非计数对象确实是去重后的项目。

### 4.3 脱敏诊断

为消息处理结果增加结构化诊断，建议字段包括：

- 消息内部 ID。
- 模型与代码版本。
- 工具名、工具调用轮次、工具调用 ID 的哈希。
- 校验错误字段路径，例如 `data.items.1.due_date`。
- 错误类型，例如 `date_type`、`extra_forbidden`、`missing`。
- 是否在后续轮次修复。
- 最终计划动作数、去重数和保存结果数。

禁止保存：API Key、企微 Secret、完整工具参数、完整群消息副本和未经脱敏的 SDK 响应。用户群回复仍只显示业务级文案。

### 4.4 回复失败与保存成功分离

消息处理状态需要拆分为：

- `processing`
- `saved`
- `replying`
- `done`
- `reply_failed`
- `failed_before_save`

保存成功后，即使企微最终回复失败，也不得把消息标成业务处理失败。状态页和日志应明确显示“已保存，回复失败”，并提供工作台检查入口。不得自动重放业务保存；只能在确认平台未接收时重试回复。

### 4.5 统一进程启动和身份

新增统一启动脚本，负责启动并检查：

1. FastAPI Web 后端。
2. Vite 前端开发服务或后端静态构建服务。
3. 企业微信接收 worker。
4. 提醒 worker。

统一启动器必须：

- 只加载一次 `.env`。
- 把同一个绝对 `TRACKER_DB` 传给所有后端进程。
- 启动前检查端口、进程租约和重复实例。
- 为各进程建立独立日志文件和 PID/启动时间记录。
- 在状态接口展示数据库路径哈希、代码版本、进程启动时间和最近心跳。
- 退出或重启时只操作由该启动器创建的进程。

企微启用时，配置检查必须拒绝 `localhost`、`127.0.0.1` 和其他员工手机不可访问的 `TRACKER_WEB_URL`，并提示配置局域网地址或 HTTPS 域名。

### 4.6 修复提醒负责人契约

推荐把提醒记录的收件人改为可空系统用户引用：

- `owner_id` 允许为空。
- 无系统用户 ID 时创建 `blocked` 提醒记录，详情为“负责人未绑定系统成员”。
- `dispatch` 只处理存在有效 `owner_id` 和企微 UserID 的记录。
- 管理页集中展示阻塞提醒，指导管理员完成绑定。
- 后续负责人结构中增加可选的系统用户 ID；姓名和 A/B 角继续用于展示，系统 ID 用于权限与发送。

SQLite 迁移需要重建 `reminders` 表，在事务中复制数据、重建索引并核对行数。迁移前必须执行在线备份，不得直接覆盖唯一数据库文件。

## 5. 数据流

```text
企微回调
  → 回调和身份校验
  → 消息幂等检查
  → AI 候选调用（只在内存）
  → 参数校验、模型修正、业务去重
  → 最终执行计划
  → 权限与版本预检
  → 逐动作保存并记录业务结果
  → 持久化消息处理摘要
  → 生成准确群回复
  → 发送回复并单独记录回复状态
```

任何模型格式错误必须止于“参数校验、模型修正”阶段；任何企微发送错误必须发生在业务保存完成之后，并拥有独立状态。

## 6. 测试与验收

### 6.1 AI 规划测试

- “明后两天去锐翰工厂调研”只形成两个最终事项。
- 模型先返回错误结构、再返回正确结构时，只统计最终正确动作。
- 同一事项被模型重复调用时只保存一次。
- 模型所有轮次都无法修正时保存 0 项，并返回可重试提示。
- 失败诊断包含字段路径和错误类型，不包含字段值和原文。

### 6.2 批量业务测试

- 两个合法动作均保存时，回复为识别 2、保存 2、失败 0。
- 一个动作存在版本冲突时，只把该动作计为业务失败。
- 重放同一个企微 `msgid` 不产生新项目、节点或审计记录。
- 相同文本使用新的消息编号时，业务指纹避免十分钟内重复新增。

### 6.3 回复状态测试

- 保存成功、最终回复失败时，消息状态为 `reply_failed`，项目仍只保存一次。
- 回复重试不得重新调用模型或重新执行业务动作。
- SDK 断线和超时日志不包含凭证与完整消息正文。

### 6.4 进程一致性测试

- 四个进程显示同一个数据库路径哈希。
- 重复启动企微接收进程被拒绝并明确指出现有实例。
- 状态页能区分未启动、离线、已认证、消息处理错误和回复错误。
- `TRACKER_WEB_URL` 为回环地址时，企微启动检查失败。

### 6.5 提醒测试

- `owner_id` 为空时创建阻塞记录而不是抛出 `IntegrityError`。
- 一个无负责人节点不会阻止其他节点生成提醒。
- 自动完成成功、提醒扫描失败时必须分别记录结果，周期日志不能只显示笼统失败。
- 负责人绑定后，下一次扫描把阻塞记录转为可发送状态。

## 7. 实施顺序

### 第一阶段：阻止误导和重复写入

- 分离模型尝试与最终业务计划。
- 对最终计划去重。
- 修正批量计数和企微回复文案。
- 增加对应单元测试和集成测试。

### 第二阶段：增加可诊断性

- 增加脱敏字段级校验诊断。
- 拆分保存状态和回复状态。
- 改进企微 worker 日志与状态接口。

### 第三阶段：统一运行方式

- 增加统一启动、停止和状态检查脚本。
- 增加数据库路径哈希和代码版本标识。
- 对企微工作台地址执行非回环校验。

### 第四阶段：修复提醒数据契约

- 备份数据库。
- 迁移提醒表的可空负责人设计。
- 修复扫描和发送过滤逻辑。
- 增加管理页阻塞原因展示。

## 8. 非目标

- 不更换 DeepSeek 服务商。
- 不引入消息队列或多机分布式架构。
- 不允许模型直接访问数据库、网络或文件。
- 不自动猜测姓名对应的系统用户账号。
- 不在日志中保存密钥或完整模型工具参数。
- 不把整个项目的完成状态改为自动确认；本蓝图只保留现有节点自动完成规则。

## 9. 完成标准

本方案完成后，同样的“明后两天”消息必须只产生两个节点，群回复必须显示“识别 2 项、保存 2 项、失败 0 项”。模型内部发生多少次格式修正都不能改变业务计数。后台必须能通过脱敏诊断指出失败字段；企微回复失败不得导致重复保存；提醒扫描遇到未绑定负责人时不得中断整个周期；所有后台进程必须能证明它们使用同一个数据库实例。
